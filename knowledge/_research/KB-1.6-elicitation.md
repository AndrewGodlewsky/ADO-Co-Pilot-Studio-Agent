## Field inheritance / ADO defaults that flow down (NEW load-bearing claims for this doc)

- A Task inherits its parent backlog item's **Area Path** and **Iteration Path** automatically, and appears on sprint taskboards: "Tasks inherit the parent's **Area Path** and **Iteration Path** and appear on sprint taskboards." — *Plan and track work in Azure Boards* (Microsoft Learn) — https://learn.microsoft.com/azure/devops/boards/get-started/plan-track-work?view=azure-devops#add-tasks-child-items (2026-06-11)
- Area Path and Iteration Path are common fields that appear on **all** work item forms for every work item type; teams associate a subset of paths with a team. — *Query by area or iteration path* (Microsoft Learn) — https://learn.microsoft.com/azure/devops/boards/queries/query-by-area-iteration-path?view=azure-devops (2026-06-11)
- New work items added from a team's backlog/board are assigned the team's **Default Area Path** and **Default Iteration Path** (team defaults referenced by backlogs and boards); the set of items shown on a backlog/board depends on the team's selected area paths and the item's state/parent-child status. This is why Area Path / Iteration Path / Team behave as inheritable *defaults to confirm* rather than independently-authored fields. — *About teams and Agile tools* (Microsoft Learn) — https://learn.microsoft.com/azure/devops/organizations/settings/about-teams-and-settings?view=azure-devops#team-defaults-referenced-by-backlogs-and-boards (2026-06-11)
- Value Area is Architectural (technical services that implement business features — enabler work) or Business (default; services that directly deliver customer value); inheriting the parent's Value Area keeps a child's classification aligned with the parent's intent. — cross-ref `_research/KB-1-quality.md` (Value Area), *Agile workflow in Azure Boards* — https://learn.microsoft.com/azure/devops/boards/work-items/guidance/agile-process-workflow?view=azure-devops#define-user-stories (2026-06-11)
- Title, Description, and Acceptance Criteria are item-distinguishing fields, not inheritable: Title "summarizes the work item and helps team members distinguish it from others"; Description/Acceptance Criteria carry item-specific scope and close conditions. The Acceptance Criteria field exists on Epic/Feature/User Story/Bug but **not on Task** (Task carries Title + Description only). — cross-ref `_research/KB-1-quality.md` (Titles & descriptions; Acceptance Criteria field by type) (2026-06-11)

## Portfolio parent/child rules (cross-referenced, already grounded in KB-2)

- The Agile hierarchy is Epic → Feature → User Story → Task; Epics/Features group work, Stories/Tasks track it. — cross-ref `_research/KB-2-leveling.md`; *Define features and epics* — https://learn.microsoft.com/azure/devops/boards/backlogs/define-features-epics?view=azure-devops (2026-06-11)
- Strict parent rule: "You can only reparent backlog items under other features, and features under other epics." (A Story's parent must be a Feature; a Feature's parent must be an Epic.) — cross-ref `_research/KB-2-leveling.md`; *Organize your backlog and map child work items to parents* — https://learn.microsoft.com/azure/devops/boards/backlogs/organize-backlog?view=azure-devops (2026-06-11)
- A Feature can be created under an existing Epic. — cross-ref `_research/KB-2-leveling.md`; *Organize your backlog* — https://learn.microsoft.com/azure/devops/boards/backlogs/organize-backlog?view=azure-devops (2026-06-11)
- Sizing/time-horizon: a Story/backlog item should generally complete within a sprint; a Feature is several stories and may span one or more sprints; an Epic spans several sprints or releases. Portfolio backlogs help "minimize size variability ... by breaking down a large feature into smaller backlog items." — cross-ref `_research/KB-2-leveling.md`; *Define features and epics* — https://learn.microsoft.com/azure/devops/boards/backlogs/define-features-epics?view=azure-devops (2026-06-11)

## Story splitting / vertical slicing / SPIDR (cross-referenced, already grounded in KB-2)

- Split stories by VALUE (vertical slices) rather than by architectural layer (horizontal UI/DB/API); layer splits fail INVEST's Independent + Valuable. A vertical slice cuts through all layers to deliver a thin piece of usable functionality. — cross-ref `_research/KB-2-leveling.md`; Visual Paradigm vertical vs horizontal slicing — https://www.visual-paradigm.com/scrum/user-story-splitting-vertical-slice-vs-horizontal-slice/ ; Humanizing Work guide to splitting user stories — https://www.humanizingwork.com/the-humanizing-work-guide-to-splitting-user-stories/ (2026-06-11)
- SPIDR — five common split techniques (Spike, Paths, Interfaces, Data, Rules), attributed to Mike Cohn — useful when a candidate child is really a whole Feature that needs slicing. — cross-ref `_research/KB-2-leveling.md`; itemis SPIDR — https://blogs.itemis.com/en/spidr-five-simple-techniques-for-a-perfectly-split-user-story (2026-06-11)
- A story should be small enough that roughly 6–10 fit in a sprint; no single story should exceed ~25–33% of average velocity (right-sizing signal for "is this child Story-sized under its Feature?"). — cross-ref `_research/KB-2-leveling.md`; Agile Alliance, "Should your user stories fit into one sprint?" — https://agilealliance.org/why-you-need-your-user-stories-to-fit-into-one-sprint/ (2026-06-11)

## Quality framing for the well-formed child (cross-referenced, already grounded in KB-1)

- INVEST (Independent, Negotiable, Valuable, Estimable, Small, Testable) is the story-quality checklist used to judge the resulting child Story. — cross-ref `_research/KB-1-quality.md`; Bill Wake / XP123 — https://xp123.com/articles/invest-in-good-stories-and-smart-tasks/ (2026-06-11)
- Definition of Ready: a backlog item is "ready" when it is clear/described, has well-defined acceptance criteria, is estimated/sized, has dependencies identified, and conforms to INVEST. The gap-questions in this doc target exactly these readiness fields. — cross-ref `_research/KB-1-quality.md`; Atlassian DoR / Boost DoR (2026-06-11)
- User-voice template "As a <role>, I want <capability>, so that <value>" frames who/what/why; the "so that" clause makes the Valuable criterion explicit. — cross-ref `_research/KB-1-quality.md`; Agile Alliance INVEST glossary (2026-06-11)
- Acceptance Criteria should be independently testable with clear pass/fail outcomes; Given/When/Then (Gherkin) structures a single behavior as context → trigger → observable outcome. — cross-ref `_research/KB-1-quality.md`; Cucumber Gherkin Reference / AltexSoft (2026-06-11)
