# Work Item Type Definitions: Epic, Feature, User Story, Task

## Summary
In the Azure DevOps Agile process, work is organized into four nested levels: **Epic → Feature → User Story → Task**. An Epic is a large initiative spanning multiple releases; a Feature is a significant piece of user-facing functionality that may take one or more sprints; a User Story is a single unit of customer value that should fit within one sprint; and a Task is a small implementation step, typically a day or less, used to break a story down during sprint planning. Each level differs in size, time horizon, the audience that cares about it, and the kind of value it delivers (source: Microsoft Learn, "Define features and epics" and "About work items and work item types").

**Also known as:** ADO work item types, backlog levels, work item hierarchy, Epic vs Feature vs Story vs Task, portfolio levels, WIT definitions, what level should this be.

## The four levels at a glance

| Level | Typical size / horizon | Who cares most | Value delivered |
| --- | --- | --- | --- |
| **Epic** | A major initiative; spans several sprints or even releases | Leadership, program managers, product owners | A strategic outcome or large business goal |
| **Feature** | A significant capability; one or more sprints | Product owners, program managers, stakeholders | A usable, shippable piece of functionality |
| **User Story** | A single unit of customer value; fits in one sprint | The delivery team and the user/customer | One concrete slice of customer-facing value |
| **Task** | An implementation step; about a day or less | Individual developers/testers on the team | Progress toward completing one story |

Epics and Features are *portfolio* levels used to group and roll up work. User Stories and Tasks are the *delivery* levels the team executes day to day (source: Microsoft Learn, "About work items and work item types"; "Change a project process from Basic to Agile").

## Epic

An Epic is **a large body of work that can be broken down into multiple Features. It represents a major initiative or goal and might span several sprints or even releases** (source: Microsoft Learn, "Define features and epics"). Epics answer "what big outcome are we pursuing?" rather than "what will we build this sprint?"

- **Size / horizon:** the largest level; measured in features, not stories; lives across releases.
- **Who cares:** leadership, program managers, and product owners tracking a portfolio.
- **Value:** a strategic outcome (for example, an initiative or program), not a single shippable increment.
- **Children:** Features.

In this agent's scope, Epics are read-only: the agent reads existing Epics to parent Features beneath them but does not create or modify the Epic itself. See *2.3 Hierarchy and Parenting Rules*.

## Feature

A Feature is **a significant piece of functionality that delivers value to the user. It typically includes several user stories or backlog items and might take one or more sprints to complete** (source: Microsoft Learn, "Define features and epics"). A Feature is the level at which a coherent, demonstrable capability lives.

- **Size / horizon:** spans one or more sprints; composed of several stories.
- **Who cares:** product owners, program managers, and stakeholders watching capability-level progress.
- **Value:** a complete, user-facing capability that can be released and described in product terms.
- **Parent:** an Epic. **Children:** User Stories.

A Feature rolls up the progress of its stories, giving stakeholders a portfolio-level view (source: Microsoft Learn, "Define features and epics," rollup columns).

## User Story

A User Story captures **a unit of customer-facing value to plan and deliver** (source: Microsoft Learn, "Use backlogs to manage projects"). Stories sit on the product backlog and are the requirement-level work item for the Agile process. General agile guidance holds that a story should be small enough to **complete within a single sprint** while still delivering value (source: Microsoft Learn, "Define features and epics"; Agile Alliance, "Should your user stories fit into one sprint?").

- **Size / horizon:** fits inside one iteration; small enough that several stories fit in a sprint.
- **Who cares:** the delivery team building it and the user receiving the value.
- **Value:** one concrete, independently valuable slice of customer value (a vertical slice, not an architectural layer).
- **Parent:** a Feature. **Children:** Tasks.

## Task

A Task is the smallest level, used to **break down planned work into distinct units** during sprint planning. Tasks can include development, testing, and other kinds of work, and are estimated with **Remaining Work** in hours or days (source: Microsoft Learn, "Agile workflow in Azure Boards — Define tasks"). Microsoft's sprint-planning guidance is explicit: **"Size tasks to take no more than a day. If a task is too large, break it down"** (source: Microsoft Learn, "Add tasks to backlog items for sprint planning").

- **Size / horizon:** about a day or less of work; lives within a single sprint.
- **Who cares:** the individual contributor doing the work.
- **Value:** no standalone customer value — a Task is a step toward completing its parent story.
- **Parent:** a User Story. (Tasks inherit the parent's Area Path and Iteration Path and appear on the sprint taskboard — source: Microsoft Learn, "Plan and track work — Add tasks.")

## How the levels relate

Stories roll up into Features; Features roll up into Epics; Tasks roll up into Stories (source: Microsoft Learn, "Define features and epics"). When choosing a level, work *down* from the value being described: a strategic outcome is an Epic, a shippable capability is a Feature, a single slice of user value is a Story, and a concrete build step is a Task. For the signals that tell you when an item is at the wrong level, see *2.2 Right-Sizing Signals*; for worked corrections, see *2.4 Common Type Mismatches*.
