# Hierarchy and Parenting Rules

## Summary
The Azure DevOps Agile hierarchy is strict and one-directional: **a Task's parent is a User Story, a User Story's parent is a Feature, and a Feature's parent is an Epic**. Microsoft states the constraint plainly — **"You can only reparent backlog items under other features, and features under other epics"** (source: Microsoft Learn, "Organize your backlog and map child work items to parents"). A new Feature can be created and linked under an existing Epic. In this agent's scope, Epics are read-only: existing Epics are read to use as parents, but the Epic work item itself is not created or modified.

**Also known as:** parenting rules, parent-child links, hierarchy rules, link a feature to an epic, who is the parent, reparenting, work item linking, backlog levels.

## The parent-of rule

Each Agile backlog level has exactly one valid parent level:

| Child work item | Valid parent |
| --- | --- |
| **Task** | **User Story** |
| **User Story** | **Feature** |
| **Feature** | **Epic** |
| **Epic** | (top level — no parent in this hierarchy) |

This is not a convention but a structural rule of the Agile process. Microsoft's backlog guidance states you can **only** reparent backlog items (stories) under Features, and Features under Epics (source: Microsoft Learn, "Organize your backlog"). The Azure Boards FAQ explains why: **"Each process defines default backlog levels... Work item types assigned to those backlog levels naturally form parent-child relationships"** (source: Microsoft Learn, "Azure Boards FAQs").

The relationship is created with the **Parent/Child** link type — the link category that forms the hierarchy — set via a Parent or Child link on the work item, the backlog mapping pane, or by dragging within the tree (source: Microsoft Learn, "Link work items to objects").

## Tasks under User Stories

Tasks are created to break a story down for sprint execution. A Task **inherits its parent story's Area Path and Iteration Path** and appears on the sprint taskboard (source: Microsoft Learn, "Plan and track work — Add tasks (child items)"). A Task created without a parent becomes an **unparented task** that sits at the top of the taskboard until it is dragged onto — that is, parented to — a backlog item (source: Microsoft Learn, "Add tasks to backlog items for sprint planning — Unparented tasks"). Tasks should therefore be attached to the User Story whose value they help deliver.

## User Stories under Features

User Stories are the requirement-level backlog items; grouping them under Features gives a portfolio-level rollup of scope and progress. Product owners and program managers **map User Stories to Features** for higher-level planning (source: Microsoft Learn, "Agile workflow in Azure Boards — Map user stories to features"). A Story's parent is always a Feature — never an Epic directly, and never another Story.

## Features under Epics: linking a new Feature to an existing Epic

A Feature's parent is an Epic. A new Feature can be **created directly under an existing Epic** — for example, "create a feature under epic #50" is a supported pattern, after which child stories are added beneath the new Feature (source: Microsoft Learn, "Organize your backlog — Use AI to organize your backlog"). The workflow is:

1. Identify the existing target Epic (read it; do not modify it).
2. Create the Feature.
3. Link the Feature to the Epic with a **Parent** link to the Epic (equivalently, a **Child** link from the Epic), or set the parent via the mapping pane / drag in the backlog tree (source: Microsoft Learn, "Link work items to objects").

This lets new capability work roll up into an established initiative without changing the initiative record itself.

## Epics are read-only in this agent's scope

In this agent's scope, Epics are read-only. The agent reads existing Epics so a new Feature can be parented beneath them, but it does not create or modify the Epic work item. Azure DevOps itself fully supports Epics as the top portfolio level — the Agile process defines both Epic and Feature portfolio backlogs (source: Microsoft Learn, "Change a project process from Basic to Agile"). The read-only treatment here is a scope fact about this agent, not a limitation of Azure DevOps. A request that is genuinely Epic-sized is re-leveled into a Feature; see *2.4 Common Type Mismatches* for the worked case.

## What is NOT allowed by the hierarchy

- A Task parented directly to a Feature or Epic (Tasks belong under Stories).
- A User Story parented directly to an Epic (Stories belong under Features).
- A Feature parented under another Feature, or a Story under another Story (levels don't nest into themselves in the standard Agile hierarchy).

When an item appears to need one of these "skip-level" or same-level parentings, the real issue is usually a leveling mismatch — the item is at the wrong level. Re-level it first (see *2.2 Right-Sizing Signals* and *2.4 Common Type Mismatches*), then parent it under the correct level.

For the definitions of each level, see *2.1 Work Item Type Definitions*.
