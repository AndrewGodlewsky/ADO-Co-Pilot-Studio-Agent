# Right-Sizing Signals: Is This the Correct Level?

## Summary
The single most useful right-sizing test is the **"fits in one iteration?"** check: a User Story should be completable within one sprint, while Features and Epics may take one or more sprints (source: Microsoft Learn, "Define features and epics"). An item that is too big shows signals like "and/or" in the title, multiple user roles, or many acceptance criteria, and should be split; an item that is too small shows signals like "no standalone user value" or "a single build step," and belongs as a Task under a story. This document lists the too-big and too-small signals for each level and how to split or merge accordingly.

**Also known as:** right-sizing, story sizing, fits in one sprint, too big too small, splitting stories, decomposition, slicing work, INVEST, when to split a feature, vertical slice.

## The core test: "Fits in one iteration?"

Microsoft's guidance is direct: **"Generally, you should complete backlog items, such as user stories or tasks, within a sprint, while features and epics might take one or more sprints to complete"** (source: Microsoft Learn, "Define features and epics"). Use that boundary as the primary sort:

- Completable in **one sprint** with demonstrable user value → **User Story**.
- Needs **one or more sprints** and groups several stories → **Feature**.
- Spans **several sprints or releases** and groups several features → **Epic**.
- Completable in **roughly a day** as a build step under a story → **Task** (source: Microsoft Learn, "Add tasks to backlog items for sprint planning": *"Size tasks to take no more than a day"*).

General agile sizing adds a useful sanity check: a story should be small enough that several (roughly 6–10) fit in a sprint, and no single story should dominate the sprint — a common rule of thumb is that one story shouldn't exceed about 25–33% of the team's average velocity (source: Agile Alliance, "Should your user stories fit into one sprint?"; Humanizing Work, "Guide to splitting user stories").

## Too-big signals (the item should move UP or be SPLIT)

Watch for these in a proposed Story (it may really be a Feature) or a proposed Feature (it may really be an Epic):

- **Conjunctions in the title:** "and," "or," "plus," commas joining capabilities — each clause is often its own item.
- **Multiple user roles or personas** served by one item.
- **Multiple workflows or end-to-end scenarios** bundled together.
- **A long acceptance-criteria list** that reads like several independent outcomes.
- **"Won't fit in a sprint"** — the team can't see finishing it in one iteration.
- **Spans multiple teams or components** to deliver.
- **Naming that describes an initiative or theme** rather than one concrete capability or value slice.

The more of these that fire, the higher the correct level. Microsoft frames portfolio backlogs as the tool to **"minimize size variability of your deliverables by breaking down a large feature into smaller backlog items"** (source: Microsoft Learn, "Define features and epics").

## Too-small signals (the item should move DOWN or become a TASK)

Watch for these in a proposed Story that is really a Task:

- **No standalone user value** — nobody outside the team would notice it shipped on its own.
- **It is a single technical step:** "create the table," "add the endpoint," "write the unit tests," "update the config."
- **It is phrased as an activity** (a verb-led build step) rather than an outcome a user receives.
- **It only makes sense as part of a larger story** — it's one slice of how a story gets built.
- **It is naturally estimated in hours**, not in relative story value.

A Task is "a distinct unit of planned work" estimated in Remaining Work hours and lives under a story (source: Microsoft Learn, "Agile workflow in Azure Boards — Define tasks"). If an item has no user-facing value and is a build step, it is a Task, not a Story.

## Splitting a Feature into Stories

When a Feature is confirmed (multi-sprint, several capabilities), split it into Stories that each deliver one slice of value. The durable rule from agile practice: **split by value (vertical slices), not by architectural layer**. Splitting into "UI story / database story / API story" fails because those layers aren't independently valuable; slice so each story delivers a usable thin path through the whole stack (source: Visual Paradigm, "Vertical vs horizontal slicing"; Humanizing Work).

Common split patterns (the SPIDR set, attributed to Mike Cohn — source: itemis, "SPIDR"):

- **Spike** — separate the research/unknown from the deliverable.
- **Paths** — split distinct workflows or paths through the feature.
- **Interfaces** — split by interface, device, or channel.
- **Data** — split by data type or data variation handled.
- **Rules** — defer or separate business rules and edge cases.

Each resulting Story should pass the "fits in one sprint" test and stand on its own as customer value.

## Merging trivial Stories into Tasks

The inverse problem: several "stories" that are really steps of one deliverable. If items have no independent user value and only make sense together (for example, "build the form," "validate the form," "save the form"), they are Tasks of a single Story — the Story being the value the user actually receives ("submit the form"). Re-level the value-bearing item to a User Story and attach the steps as child Tasks (source: Microsoft Learn, "Plan and track work — Add tasks (child items)"; "Add tasks to backlog items for sprint planning").

## Quick decision flow

1. **Does it deliver standalone user value?** No → it's a **Task** under the relevant Story. Yes → continue.
2. **Does it fit in one sprint?** Yes → **User Story**. No → continue.
3. **Is it one coherent capability that groups several stories (one-or-more sprints)?** Yes → **Feature**. 
4. **Is it a multi-feature, multi-sprint/release initiative?** Yes → **Epic** (read-only in this agent's scope; re-level to a Feature — see *2.4 Common Type Mismatches*).
