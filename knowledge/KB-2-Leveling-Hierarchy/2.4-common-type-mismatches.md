# Common Type Mismatches and Their Corrections

## Summary
Three leveling mismatches account for most wrong-type work items: a **Task that's really a User Story** (it has standalone user value), a **User Story that's really a Feature** (it can't fit in one sprint and bundles several capabilities), and an **Epic-sized request** (a multi-sprint, multi-feature initiative). Each has a tell-tale signal and a corrective move. This document works through all three, grounded in the size and horizon boundaries from Microsoft Learn ("Define features and epics") and general agile splitting practice.

**Also known as:** wrong work item type, type mismatch, mislabeled item, task vs story, story vs feature, epic-sized request, re-leveling, corrective examples, this is too big.

## How to read each case

For each mismatch: the **signal** that reveals it, **why** it's mislabeled, and the **corrective move**. Use these alongside the signal lists in *2.2 Right-Sizing Signals*.

## Case 1 — A Task that's really a User Story

**Example request:** "Add a Task: *Let customers reset their own password.*"

**Signal that reveals it:** the item delivers **standalone, customer-facing value**. A user would notice and benefit if it shipped — that's the hallmark of a Story, not a Task. A genuine Task has no independent value; it's a build step like "add the reset endpoint" or "write the reset-email template" (source: Microsoft Learn, "Agile workflow — Define tasks," where Tasks are implementation units estimated in Remaining Work hours).

**Why it's mislabeled:** Tasks describe *how* the team builds something and live under a Story; this item describes *what value the user gets*, which is the Story level (source: Microsoft Learn, "Use backlogs to manage projects," where the backlog item captures "a unit of customer-facing value").

**Corrective move:** Re-level the item to a **User Story** ("Customer can reset their own password"). Parent it under the appropriate Feature. The original build steps become child **Tasks** of that Story ("add reset endpoint," "send reset email," "add reset UI," "write tests").

## Case 2 — A User Story that's really a Feature

**Example request:** "Add a User Story: *Build the full customer account portal — profile, billing, notifications, and order history.*"

**Signal that reveals it:** the item **won't fit in one sprint** and bundles **several distinct capabilities** (note the conjunctions and the list of areas). Microsoft's boundary is that backlog items/stories should complete **within a sprint**, while Features **take one or more sprints** and **include several user stories** (source: Microsoft Learn, "Define features and epics"). Multiple personas, multiple workflows, or a long acceptance-criteria list are the supporting tells (see *2.2 Right-Sizing Signals*).

**Why it's mislabeled:** this is a coherent capability composed of several independently valuable slices — the definition of a Feature, not a single Story.

**Corrective move:** Re-level the item to a **Feature** ("Customer account portal"). **Split it into User Stories**, slicing by value (vertical slices), not by architectural layer — for example "view and edit profile," "view billing history," "manage notification preferences," "view past orders" — rather than "UI story / database story / API story" (source: Visual Paradigm, "Vertical vs horizontal slicing"; Humanizing Work, "Guide to splitting user stories"). Each Story must pass the one-sprint test. Parent the Stories under the new Feature.

## Case 3 — An Epic-sized request

**Example request:** "Add: *Modernize the entire commerce platform across web, mobile, and back office over the next few quarters.*"

**Signal that reveals it:** the request describes a **major initiative that spans several sprints or releases and groups multiple features**. Microsoft defines an Epic as **"a large body of work that can be broken down into multiple features... might span several sprints or even releases"** (source: Microsoft Learn, "Define features and epics"). Initiative- or theme-level naming, a multi-quarter horizon, and "across multiple areas/teams" are the tells.

**Why it's mislabeled (for this agent):** the request is genuinely at the Epic level. In this agent's scope, Epics are read-only — the agent does not create Epic work items (see *2.3 Hierarchy and Parenting Rules*).

**Corrective move:** Re-level the request to a **Feature** that delivers a concrete, near-term capability (one-or-more sprints), and, where one exists, parent that Feature under the relevant existing Epic. If the initiative is too large to express as one Feature, identify the single highest-value capability to start with and scope the Feature to that, leaving the broader initiative for the read-only Epic level. Then decompose the Feature into User Stories as in Case 2. The result is buildable work at levels the agent creates (Feature → Story → Task) while the strategic framing stays at the Epic level it reads but does not author.

## Mismatch-to-correction cheat sheet

| Mismatch | Tell-tale signal | Corrective move |
| --- | --- | --- |
| Task → really a Story | Has standalone user value | Re-level to User Story; original steps become child Tasks |
| Story → really a Feature | Won't fit one sprint; bundles several capabilities | Re-level to Feature; split into vertical-slice Stories |
| Epic-sized request | Multi-sprint/release, multi-feature initiative | Re-level to a near-term Feature under the existing Epic; decompose into Stories |

The common thread: **fix the level first, then parent under the correct level.** A parenting problem (for example, wanting to attach a Story straight to an Epic) is usually a leveling problem in disguise. See *2.2 Right-Sizing Signals* for the full signal lists and *2.1 Work Item Type Definitions* for what each level is.
