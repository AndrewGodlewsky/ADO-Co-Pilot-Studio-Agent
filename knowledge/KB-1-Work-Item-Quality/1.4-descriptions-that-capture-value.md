# Descriptions That Capture Value

## Summary
A strong work-item Description explains the outcome and value — who the work is for, what they want to accomplish, and why — rather than prescribing how to build it (per Microsoft Learn: Agile workflow in Azure Boards). Its job is to give a newcomer enough context to estimate the work and write tasks and tests without hunting down the author. For Features and User Stories the Description focuses on customer value; for Tasks, where work is concrete and technical, the Description names the specific unit of work and what "done" looks like. Implementation detail belongs in the Description only when it is genuinely needed for shared understanding, not as a substitute for the value the item delivers.

**Also known as:** description, work-item description, story description, details, context, background, the "why," value statement, problem statement.

## What a Description Is For
Azure DevOps guidance for User Stories is explicit: "provide enough detail for estimating how much work is required... Focus on who the feature is for, what users want to accomplish, and why. Don't describe how the feature should be developed. Do provide sufficient details so your team can write tasks and test cases" (per Microsoft Learn: Agile workflow in Azure Boards). The same principle applies across the backlog — when defining a backlog item, focus on customer value and avoid describing implementation details (per Microsoft Learn: Manage Scrum process work item types & workflow).

A good Description therefore captures:

- **Who** benefits — the user, role, or stakeholder.
- **What** they want to accomplish — the outcome, not the mechanism.
- **Why** it matters — the value, problem solved, or motivation.
- **Enough context** that a team member new to the item can estimate it and derive tasks and tests.

The "newcomer test" is a useful lens: could someone who was not in the conversation read the Description and understand the item's purpose, scope, and value? If they would have to ask the author basic questions, the Description is incomplete.

## Outcome and Value Over Implementation
The most common Description weakness is describing *how* instead of *why*. "Add a column to the orders table" tells a reader nothing about the value at stake; "let customers see estimated delivery dates so they trust their order will arrive on time" does. Implementation detail is not banned — the Description field supports rich text and images and is a powerful tool for specifying work (per Microsoft Learn: cloud-native DevOps) — but at the Feature and Story level it should support the value statement, not replace it. Detailed *how* is the job of child Tasks and of the team's design discussion (the "Negotiable" property of a good story).

For higher levels, Microsoft's guidance is to enter enough detail to help the team understand scope, estimate work, and develop tests (per Microsoft Learn: Define features and epics). Value Area (Architectural or Business) complements the Description by recording the kind of customer value the item addresses (per Microsoft Learn: Define features and epics).

## The Context a Newcomer Needs
Beyond who/what/why, a Description often needs supporting context so the item stands on its own:

- **Background** — the situation or problem that prompted the item.
- **Scope signals** — what is included and, where it prevents confusion, what is explicitly out of scope.
- **Constraints or assumptions** — anything that shapes the solution space (without dictating the solution).
- **References** — links to designs, related items, or data, attached or linked rather than pasted at length.

The goal is self-sufficiency: the item should be understandable without its author present.

## Examples by Type
Each type shows a good Description and a bad one with its fix.

### Feature
A Feature should convey customer-facing value and enough scope to break into stories (per Microsoft Learn: Best practices for Agile product management).

- **GOOD (Feature: order delivery estimates):** "Customers currently have no visibility into when their orders will arrive, which drives support contacts and erodes trust. This feature gives shoppers an estimated delivery date during checkout and on the order-status page, based on the shipping method and warehouse. In scope: estimate display at checkout and order status. Out of scope: real-time carrier tracking. Value Area: Business."
  - Frames the problem, the outcome, the beneficiary, and scope boundaries — enough to derive stories and estimate.
- **BAD:** "Add delivery date logic to the checkout service."
  - *Why it fails:* describes a mechanism with no who, what value, or scope; a newcomer cannot tell what problem it solves or how to size it.
  - *Fix:* the GOOD version above — lead with the customer problem and the visible outcome, then bound the scope.

### User Story
A Story's Description should focus on who/what/why and give enough detail to write tasks and tests (per Microsoft Learn: Agile workflow in Azure Boards).

- **GOOD (Story: save cart across sessions):** "As a returning shopper, I want my cart contents to persist after I sign out, so that I don't have to rebuild my order on my next visit. Today the cart clears on sign-out, which is a common reason shoppers abandon purchases. Persisting the cart should survive sign-out/sign-in on the same account; behavior for discontinued items is covered in acceptance criteria."
  - Who/what/why is explicit, the motivation is clear, and there is enough to derive tasks and tests.
- **BAD:** "Persist cart. Use Redis with a 30-day TTL and a new table."
  - *Why it fails:* it is all implementation — no user, no value — and it prematurely fixes a design that should be negotiable.
  - *Fix:* lead with the user-voice value statement (as above) and move any genuine technical constraint into child Tasks or a design note, leaving the solution open.

### Task
A Task is concrete technical work; its Description names the specific unit of work and the completion condition (Tasks carry only Title and Description and have no Acceptance Criteria field).

- **GOOD (Task: persist cart on logout):** "Add a service method that writes the current cart to durable storage when a user signs out, keyed by user ID, and restores it on next sign-in. Done when the cart round-trips through sign-out/sign-in for a signed-in user. Parent: 'Save cart across sessions.' See design note linked below."
  - Specific, self-contained, with a clear done condition and a link to its parent's value.
- **BAD:** "Cart persistence."
  - *Why it fails:* restates the title with no detail — a newcomer cannot tell what to build or when it is done.
  - *Fix:* the GOOD version above — name the concrete change, the completion condition, and the parent story.

## Common Anti-Patterns
- **Implementation-as-description** at Feature/Story level, hiding the value the item exists to deliver.
- **Empty or one-line Descriptions** that just echo the title — a Description that only restates the title adds no context for estimating the work or deriving tasks and tests.
- **No "why":** the reader cannot tell why the item matters or how to prioritize it.
- **Missing scope boundaries**, leaving the reader unsure what is and is not included.
- **Author-dependent context:** the item only makes sense to people who were in the original conversation.
