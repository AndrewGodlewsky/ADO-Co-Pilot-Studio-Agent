# Eliciting a Child from its Parent

## Summary
When a new work item is created beneath an existing one — a User Story under a Feature, or a Feature under an Epic — the parent already answers many of the questions an interview would otherwise ask. Reading the parent first turns elicitation from a long generic questionnaire into a short, sharp conversation: classification fields such as Area Path, Iteration Path, Value Area, and Team flow down as defaults to confirm, while the child's distinguishing fields — Title, Description, and Acceptance Criteria — are authored fresh and tested for alignment with the parent's scope. This document is the reference playbook for that parent-aware elicitation: the inheritance rules, a question bank per scenario, alignment and sibling-duplicate checks, and a worked dialogue for each scenario.

**Also known as:** parent-aware elicitation, eliciting from the parent, parent-grounded questions, child-from-parent, context-aware story elicitation, inheriting fields from a parent, parent context, asking fewer questions, slice of the feature, feature under an epic.

## Why the parent matters
A backlog item never exists in isolation. In the Agile hierarchy — Epic → Feature → User Story → Task — each level groups or refines the one above it (per Microsoft Learn: *Define features and epics*; cross-ref KB-2.1, KB-2.3). The parent therefore carries context the child can borrow: where the work lives (Area Path), when it is scheduled (Iteration Path), what kind of value it delivers (Value Area), which team owns it, and — most importantly — the outcome the child is meant to advance.

Good elicitation exploits this. Every field the parent already supplies is a question that does not need to be asked, so the conversation budget can go to the one thing only a human knows: which slice of the parent's value this child delivers, and how that slice will be tested. The result is fewer questions, sharper questions, and a child that is well-formed *and* aligned with its parent the moment it is created.

Two facts make this mechanical rather than hopeful. First, Area Path and Iteration Path are common fields present on every work item form, and ADO assigns team default Area Path and Iteration Path values when items are added from a team's backlog or board (per Microsoft Learn: *Query by area or iteration path*; *About teams and Agile tools*). Second, a Task inherits its parent's Area Path and Iteration Path automatically (per Microsoft Learn: *Plan and track work in Azure Boards*). So the classification fields genuinely behave as inheritable defaults; the distinguishing fields genuinely do not.

## Inheritance rules — what flows down, what never does
The table below states which fields a child can default from its parent (confirm, do not silently hard-set) and which must always be authored fresh. Feature and User Story carry Title, Description, Acceptance Criteria, Value Area, and Team, plus optional estimation fields (Story Points / Priority / Risk / Effort). A Task carries only Title and Description (cross-ref KB-1 research; KB-2.1).

| Field | Epic → Feature | Feature → Story | Notes |
|---|---|---|---|
| Area Path | inherit (confirm) | inherit (confirm) | Child defaults to the parent's area; a Task inherits it automatically in ADO (per *Plan and track work in Azure Boards*). |
| Iteration Path | optional default | inherit / current (confirm) | A Feature may span several iterations, so its default is looser; a Story usually lands in a specific sprint. A Task inherits the parent Story's Iteration Path automatically. |
| Value Area | inherit (confirm) | inherit (confirm) | Default to the parent's Business or Architectural classification so the child's value type matches the parent's intent (Value Area definitions per *Agile workflow in Azure Boards*). |
| Team | inherit (confirm) | inherit (confirm) | Default to the parent's owning team; team default Area/Iteration Paths are applied on add (per *About teams and Agile tools*). |
| **Title** | **never** | **never** | A Title exists to distinguish one item from others; each item's is distinct (per *Query by titles, IDs, and rich-text fields*). |
| **Description** | **never** | **never** | Each item carries its own who/what/why; the child's scope is narrower than the parent's. |
| **Acceptance Criteria** | **never** | **never** | Each item has its own pass/fail conditions. The Acceptance Criteria field exists on Epic/Feature/Story but not on Task. |

The principle: **classification inherits, content does not.** A field that says *where, when, what kind, and who* defaults from the parent and is confirmed in one line. A field that says *what this item is and when it is done* is always written fresh for the child. When a parent's content field is empty — for example, a Feature with no Acceptance Criteria — there is nothing to coverage-check against, so that becomes a direct question to the author rather than an inherited value (cross-ref KB-1.1 Definition of Ready, KB-1.3 Acceptance Criteria).

## Scenario question bank — a Story under a Feature
A Feature names a capability and a user outcome; the Story is one testable slice of that outcome, completable within a sprint (cross-ref KB-2.1 sizing). The questions below assume the inheritable fields are already defaulted from the Feature, so they focus on the slice, the value, and the test.

- **Slice** — Which part of the Feature's outcome does this Story deliver? (Vertical slice of value, not a horizontal layer — cross-ref KB-2.2 / KB-2.4 splitting.)
- **User-voice** — As a `<role>`, I want `<capability>`, so that `<value>`? The "so that" makes the Valuable criterion explicit (cross-ref KB-1.5 INVEST: Valuable; KB-1.2 Titles).
- **Acceptance** — What is one concrete, testable check that this slice works, expressed as Given/When/Then? (cross-ref KB-1.3 testable Acceptance Criteria.)
- **Alignment** — Does this advance the Feature's outcome directly, or is it enabler/setup work? (Enabler work is usually Architectural value or belongs under a different parent.)
- **Sibling dedupe** — How is this different from the existing sibling Stories already under the Feature?
- **Size** — Does this fit in a single sprint, or does it span several outcomes and need splitting? (Right-sizing signal — cross-ref KB-2.2; SPIDR splitting — cross-ref KB-2.4.)
- **Inherited confirm** — Area Path, Iteration Path, Value Area, and Team default from the Feature — are they right, or should any change?

Ask only the questions the Feature leaves open. If the Feature's Description already pins the slice, skip the slice question and go straight to the acceptance check.

## Scenario question bank — a Feature under an Epic
An Epic names a major initiative; the Feature is one concrete capability of that initiative, typically several Stories and one or more sprints in size (cross-ref KB-2.1 sizing). The Feature's interview is scope- and decomposability-oriented rather than test-oriented, because the Feature's own testability is delivered through its Stories.

- **Capability** — Which concrete capability of the Epic's initiative does this Feature deliver?
- **Scope boundary** — What is in scope for this Feature versus explicitly left to other Features under the Epic?
- **Value** — Is this Business value (customer-facing) or Architectural value (an enabler)? What user outcome does it serve? (Value Area definitions per *Agile workflow in Azure Boards*; cross-ref KB-1.4.)
- **Decomposability** — Roughly which Stories would sit under it? (A Feature that decomposes into a handful of Stories is well-sized; one that yields only a single Story may really be a Story — cross-ref KB-2.4.)
- **Alignment** — How does this move the Epic's initiative forward?
- **Sibling dedupe / gap** — Is it distinct from the sibling Features already under the Epic? Does it fill a capability the Epic implies but no sibling covers yet?
- **Inherited confirm** — Area Path, Value Area, and Team default from the Epic — are they right? (Iteration Path is a looser default for a Feature, which may span sprints.)

## Alignment and sibling-dedupe checks
Parent context enables five checks that a context-free interview cannot perform. They are read-only reasoning over the parent and its existing children — descriptions of what a careful author verifies, not commands.

- **Advances the parent.** A well-formed child moves the parent's outcome forward. A candidate child that does not relate to the parent's scope at all is a signal that the named parent may be wrong, or that the item belongs elsewhere.
- **Right level under the parent.** A "Story" that is really a second capability of the Epic is a Feature; a "Feature" that decomposes into a single sprint's work is a Story. When the candidate is really the parent's own level, re-leveling is the corrective move (cross-ref KB-2.4 type mismatches).
- **Hierarchy valid.** Only Story↔Feature and Feature↔Epic are valid parent/child pairs — "you can only reparent backlog items under other features, and features under other epics" (per Microsoft Learn: *Organize your backlog*; cross-ref KB-2.3). A child named under the wrong level needs the correct intermediate parent.
- **Dedupe.** Comparing the candidate's title and scope to existing siblings surfaces overlap. High overlap is worth raising so the author can state the difference — or merge.
- **Gap.** Where the parent's Description or Acceptance Criteria imply a capability that no sibling covers, that gap is a candidate for an additional child — offered, never forced.

## Worked dialogue — a Story under a Feature
**Parent (read first):** Feature #412 "Self-service password reset" · Description: *Let signed-out users reset their own password without contacting support.* · Acceptance Criteria mention a time-limited reset link and a confirmation email · Area Path, Iteration Path, Value Area (Business), and Team set on the Feature · Existing sibling Stories: "Request reset by email address", "Set a new password from a valid link".

> **User:** Make me a story for the reset email.
>
> **Parent read → inherited-field confirm:** This Story will sit under Feature #412 "Self-service password reset." I'll default its area, iteration, value area (Business), and team from the Feature — change any of those? *(User: those are fine.)*
>
> **Sharp gap question (slice):** The Feature already has Stories for requesting a reset and for setting a new password from a link. The reset email itself isn't covered yet — so this is the slice that **sends and formats the reset email**. Is that the part you mean, or did you mean validating the link in the email? *(User: sending the email with the link.)*
>
> **Sharp gap question (acceptance):** Good — one testable check: Given a user has requested a reset, When the system processes the request, Then an email containing a time-limited reset link is sent to the registered address. Anything to add — wording, sender, expiry window? *(User: link expires in 30 minutes.)*

**Resulting child (well-formed, aligned):**
- **Title:** Send password-reset email with time-limited link
- **Description (user-voice):** As a signed-out user who requested a reset, I want to receive an email containing a reset link, so that I can start resetting my password without contacting support.
- **Acceptance Criteria:** Given a user has requested a password reset, When the request is processed, Then an email containing a reset link valid for 30 minutes is sent to the registered address.
- **Inherited (confirmed):** Area Path, Iteration Path, Value Area = Business, Team — from Feature #412.
- **Alignment:** advances the Feature's outcome; distinct from both siblings; fills the previously-uncovered "email" slice. Passes INVEST — small (one sprint), valuable (explicit "so that"), testable (one Given/When/Then). (Cross-ref KB-1.5.)

## Worked dialogue — a Feature under an Epic
**Parent (read first):** Epic #88 "Customer self-service portal" · Description: *Reduce support load by letting customers manage their own account, billing, and support requests online.* · Area Path, Value Area, and Team set on the Epic · Existing sibling Features: "Account profile management", "Billing and invoices".

> **User:** Add a feature for letting customers open support tickets.
>
> **Parent read → inherited-field confirm:** This Feature will sit under Epic #88 "Customer self-service portal." I'll default its area, value area, and team from the Epic — keep those? *(User: yes.)*
>
> **Sharp gap question (scope boundary + capability):** The Epic already has Features for profile and for billing, so this one is the **self-service support requests** capability. To scope it: is it about *creating and tracking* support tickets, with live chat left to a separate Feature? *(User: yes — create, view status, and add comments. Chat is separate.)*
>
> **Sharp gap question (decomposability):** That sounds Feature-sized — it decomposes into roughly: create a ticket, view ticket status, comment on a ticket, and email notifications. Does that match your intent, or is it smaller than that? *(User: that's the set.)*

**Resulting child (well-formed, aligned):**
- **Title:** Self-service support request management
- **Description:** As a customer using the self-service portal, I want to create, track, and comment on support requests online, so that I can get help without phoning support — reducing support load (the Epic's outcome). In scope: create, view status, comment, notify. Out of scope: live chat (separate Feature).
- **Value Area:** Business (customer-facing). **Inherited (confirmed):** Area Path, Value Area, Team — from Epic #88.
- **Alignment:** advances the Epic's "reduce support load" initiative; distinct from the profile and billing siblings; fills the support-request gap. Feature-sized — decomposes into several Stories spanning one or more sprints (cross-ref KB-2.1, KB-2.2).

## When the parent is sparse or the level is wrong
Two situations break the clean flow and are worth naming. When the parent has no Description or Acceptance Criteria to inherit context from, there is nothing to slice against or coverage-check; the slice and acceptance questions are asked of the author directly, and nothing is fabricated from an empty parent. When a child is named under the wrong level — for example a request to put a Story directly under an Epic — the valid hierarchy requires a Feature in between (per *Organize your backlog*; cross-ref KB-2.3), so the corrective move is to surface the missing intermediate level rather than force an invalid parent/child link. Both are points where fewer assumptions and one clarifying question produce a better-formed child than guessing.
