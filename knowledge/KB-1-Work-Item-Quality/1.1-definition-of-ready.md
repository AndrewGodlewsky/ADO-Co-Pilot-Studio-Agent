# Definition of Ready for Work Items

## Summary
A Definition of Ready (DoR) is a shared checklist that an Azure DevOps work item meets before it is considered well-formed enough to start. A "ready" item is clear, valuable, appropriately sized, and (for Features and User Stories) carries testable acceptance criteria, so the team understands the work without guessing. Readiness criteria differ by type: a Feature is ready when its outcome and scope are framed; a User Story when who/what/why and acceptance criteria are present; a Task when its concrete unit of work and "done" condition are unambiguous. The DoR is a quality gate that reduces rework and mid-sprint surprises (per Atlassian: Definition of Ready).

**Also known as:** DoR, ready criteria, readiness checklist, "ready to pull," entry criteria, story-ready, backlog refinement gate, ready for sprint.

## What "Ready" Means
The Definition of Ready is a set of criteria a backlog item meets before it is accepted into a sprint — a quality gate ensuring the work is sufficiently detailed, understood, and actionable before development begins (per Atlassian: Definition of Ready). It is collaboratively agreed by the product owner and the team rather than imposed top-down, and Microsoft's own engineering guidance maintains a DoR so items entering a sprint share a common understanding, have acceptance criteria, are estimable, and carry no blocking dependencies (per Microsoft Code-With Engineering Playbook: Definition of Ready).

Readiness is about *enough* clarity, not perfection. Agile requirements evolve, and teams typically provide full detail only for the highest-priority items or those assigned to the current and next sprint (per Microsoft Learn: Manage Scrum process work item types & workflow). A "ready" item is one a competent team member could pick up and begin without needing to track down the author for missing context.

A common foundation for a DoR is the INVEST checklist — Independent, Negotiable, Valuable, Estimable, Small, Testable — which many teams use as the backbone of their readiness criteria (per Boost: Definition of ready for Agile user stories). See the companion document on INVEST for the per-letter checks.

## Readiness by Work-Item Type
Different levels of the hierarchy (Epic → Feature → User Story → Task) carry different fields and serve different purposes, so what makes each "ready" differs. Features and User Stories carry Title, Description, Acceptance Criteria, and Value Area, plus optional estimation fields (Story Points / Effort, Priority, Risk). Tasks carry only Title and Description (per Microsoft Learn: Agile workflow in Azure Boards).

### Feature — Ready Criteria
A Feature represents a significant, customer-facing piece of functionality that delivers value and may span several user stories and one or more sprints (per Microsoft Learn: Define features and epics). A Feature is ready when:

- **Outcome is framed.** The Description states the capability and the business or user value it delivers, not the implementation. Microsoft's guidance is to enter enough detail to help the team understand scope, estimate work, and develop tests (per Microsoft Learn: Define features and epics).
- **Scope boundaries are visible.** What the Feature includes — and, where helpful, what it explicitly excludes — is clear enough to break it into child stories.
- **Value Area is set** to the area of customer value (Architectural or Business) so prioritization is meaningful (per Microsoft Learn: Define features and epics).
- **Acceptance criteria exist at the Feature level**, describing the observable result that signals the Feature as a whole is delivered. The Acceptance Criteria field is available on Features (per Microsoft Learn: Query by titles, IDs, and rich-text fields).
- **It is decomposable.** The Feature can plausibly be split into stories that each fit within a sprint; if it cannot, it is closer to an Epic and needs breaking down.

### User Story — Ready Criteria
A User Story is team-scoped work that should generally be completable within a single sprint (per Microsoft Learn: Define features and epics). A User Story is ready when:

- **Who / what / why are present.** The Description focuses on who the feature is for, what the user wants to accomplish, and why — not how it should be built (per Microsoft Learn: Agile workflow in Azure Boards). The user-voice form ("As a … I want … so that …") is the conventional way to capture this.
- **Acceptance criteria are testable.** Clear criteria define what must be true before the story can be closed, written so they yield pass/fail acceptance tests (per Microsoft Learn: Agile workflow in Azure Boards). See the companion document on testable acceptance criteria.
- **It is estimable.** There is enough detail for the team to size the work; a story that cannot be estimated usually hides an unanswered question or is too large (per Boost: INVEST criteria).
- **It is appropriately small.** The story fits within a sprint; oversized stories are split before they are considered ready.
- **Dependencies are known.** Any blocking dependency on other stories or external work is identified, because dependent work does not deliver value until all linked items complete (per Boost: INVEST criteria).
- **Value Area is set**, and optional fields (Story Points, Priority, Risk) are filled in where the team relies on them.

### Task — Ready Criteria
A Task captures developer-level work that fits within an iteration and is the technical decomposition of a story (per Microsoft Learn: Best practices for Agile product management). Tasks carry only Title and Description and do not have a formal Acceptance Criteria field. A Task is ready when:

- **It names one concrete unit of work.** The Title describes a single, specific activity, not a vague area.
- **"Done" is unambiguous.** Because there is no Acceptance Criteria field, the Description (or Title) makes the completion condition obvious — the point at which the task can be checked off without debate.
- **It connects to its parent.** The Task clearly contributes to delivering its parent story, so its purpose is visible.
- **It is self-contained enough to start.** Any inputs, links, or context the developer needs are referenced; the Description field supports rich text and images for this purpose (per Microsoft Learn: cloud-native DevOps).

## Why a DoR Helps
A clear readiness bar lets teams plan sprints with confidence, reduces miscommunication, and avoids the backtracking that comes from starting underspecified work (per Atlassian: Definition of Ready). It pairs with a Definition of Done: the DoR governs what is good enough to *start*, while the Definition of Done governs what is good enough to *finish*. For Azure DevOps specifically, a story is closed only when the product owner agrees it was implemented according to its Acceptance Criteria and acceptance tests pass — which is only possible if those criteria were present and testable when the story became ready (per Microsoft Learn: Agile workflow in Azure Boards).

## Quick Reference
| Type | Core readiness signals |
| --- | --- |
| Feature | Outcome + value framed; scope boundaries clear; Value Area set; Feature-level acceptance criteria; decomposable into sprint-sized stories |
| User Story | Who/what/why in Description; testable acceptance criteria; estimable; small enough for a sprint; dependencies known; Value Area set |
| Task | One concrete unit of work; unambiguous "done"; clearly tied to its parent story; inputs/links referenced |
