# Writing Great Work-Item Titles

## Summary
A strong Azure DevOps title summarizes the work specifically enough to tell it apart from every other item at a glance (per Microsoft Learn: Query by titles, IDs, and rich-text fields). Good titles are concrete and outcome-focused: they name what changes and for whom, not vague areas or restated field names. User Story titles read well in the user-voice form ("As a … I want … so that …"), Feature titles name a customer-facing capability, and Task titles name one concrete action. The Title is the only required field on every work-item type and is capped at 255 characters (per Microsoft Learn: About work items).

**Also known as:** title, work-item name, summary line, story title, naming work items, good titles, headline, item name.

## What a Good Title Does
The Title is "a short description that summarizes the work item and helps team members distinguish it from others" (per Microsoft Learn: Query by titles, IDs, and rich-text fields). Because titles are what people scan in backlogs, boards, queries, and rollups, a good title carries enough meaning on its own — without opening the item — to tell *what* the work is and, ideally, *who benefits* or *what outcome* it produces.

Strong titles share a few traits:

- **Specific, not generic.** "Fix login" could mean dozens of things; a good title names the actual change.
- **Outcome- or capability-focused.** Features and stories describe value delivered; tasks describe a concrete action.
- **Distinguishable.** Two items should not share a title. Near-duplicate titles ("Login", "Login 2") make boards and queries ambiguous.
- **Concise.** Within the 255-character limit, but in practice far shorter — a scannable headline, with detail living in the Description and Acceptance Criteria.
- **Free of throwaway prefixes** like "TBD" or placeholder text, which signal an item that is not yet ready.

The title is a headline, not a specification. Depth belongs in the Description (and, for Features and Stories, Acceptance Criteria), where there is room for who/what/why and detail (per Microsoft Learn: Agile workflow in Azure Boards).

## The User-Voice Form (User Stories)
User Stories describe work from the user's perspective. The conventional user-voice template makes who/what/why explicit:

> **As a** *\<type of user\>*, **I want** *\<goal\>*, **so that** *\<reason / benefit\>*.

This form mirrors Azure DevOps guidance to focus the story on who the feature is for, what users want to accomplish, and why (per Microsoft Learn: Agile workflow in Azure Boards). The full template often lives in the Description; the Title can carry a compact version of the same intent (the goal and beneficiary) so it stands alone on a board. Titles for Features and Tasks do not use the user-voice form — Features name a capability, Tasks name an action.

## Examples by Type
Each type below shows at least one GOOD title and one BAD title, with the fix for the bad one.

### Feature
A Feature names a significant, customer-facing capability that delivers value (per Microsoft Learn: Best practices for Agile product management).

- **GOOD:** `Self-service password reset for customer portal users`
  - Names a capability and who it serves; scannable; distinguishable.
- **GOOD:** `Bulk export of order history to CSV`
  - Concrete outcome, clear scope.
- **BAD:** `Authentication improvements`
  - *Why it fails:* vague — "improvements" names no capability and no outcome; cannot be distinguished from other auth work.
  - *Fix:* `Add single sign-on (SSO) login for portal users` — names the specific capability and the beneficiary.

### User Story
A User Story is sprint-sized work framed from the user's perspective.

- **GOOD:** `As a returning shopper, I want to save my cart so that I can check out later`
  - User-voice form; who/what/why visible in the title itself.
- **GOOD:** `Shopper can filter search results by price range`
  - A compact capability statement that still reads as user value (acceptable when the full user-voice template lives in the Description).
- **BAD:** `Cart stuff`
  - *Why it fails:* not specific, no user, no outcome; indistinguishable from any other cart item.
  - *Fix:* `As a shopper, I want my cart to persist across sessions so that I don't lose selected items` — restores who/what/why and makes the item unique.
- **BAD:** `Update the database`
  - *Why it fails:* describes implementation, not user value, and reads like a task, not a story.
  - *Fix:* `As an account holder, I want my updated email saved so that I receive notifications at the new address` — reframes around the user-visible outcome.

### Task
A Task names one concrete unit of developer-level work that fits within an iteration (per Microsoft Learn: Best practices for Agile product management). Tasks carry only Title and Description.

- **GOOD:** `Add unique index on Users.Email column`
  - One specific, actionable change; "done" is obvious from the title.
- **GOOD:** `Write unit tests for cart-persistence service`
  - Single, concrete activity.
- **BAD:** `Backend`
  - *Why it fails:* names an area, not an action; impossible to know when it is done.
  - *Fix:* `Implement REST endpoint to persist cart on logout` — names the specific action and its completion condition.
- **BAD:** `Misc fixes`
  - *Why it fails:* bundles unknown work under a placeholder; not distinguishable and not estimable.
  - *Fix:* split into specific tasks, e.g. `Fix null-reference error in cart total calculation`.

## Common Anti-Patterns
- **Restating the type or field name:** "User Story for cart" adds nothing — the type is already shown.
- **Placeholder titles:** "TBD", "Temp", "New work item" indicate an item that is not ready.
- **Overstuffing the title:** cramming acceptance detail into the title instead of the Description makes boards unreadable. Keep the headline tight; put detail where it belongs.
- **Implementation-only Story titles:** "Update the DB" hides the user value a story exists to deliver.
- **Vague scope words:** "improvements", "stuff", "various", "misc" — each signals undefined scope.
