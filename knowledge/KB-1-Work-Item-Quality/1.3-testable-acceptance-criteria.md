# Testable Acceptance Criteria

## Summary
Acceptance criteria define what must be true before a Feature or User Story can be closed, written clearly enough that they become pass/fail acceptance tests (per Microsoft Learn: Agile workflow in Azure Boards). The Given/When/Then structure (from Gherkin/BDD) is a reliable way to make criteria testable: Given a starting context, When an action occurs, Then an observable outcome follows (per Cucumber: Gherkin Reference). The testability test is simple — if you cannot describe a concrete pass and fail, the criterion is not yet testable. In Azure DevOps the Acceptance Criteria field exists on Features and User Stories but not on Tasks; Tasks instead need an unambiguous "done" condition in their Title or Description.

**Also known as:** acceptance criteria, AC, Given/When/Then, GWT, Gherkin scenarios, conditions of satisfaction, done criteria, BDD scenarios, testable criteria.

## Why Acceptance Criteria Matter
Acceptance criteria record the conditions to be met before a work item can be closed. Azure DevOps guidance is to describe customer acceptance criteria as clearly as possible before work begins, because conversations to define them help the team and customers share a common understanding of expectations — and the criteria then serve as the basis for acceptance tests (per Microsoft Learn: Agile workflow in Azure Boards). A user story reaches Closed only when the product owner agrees it was implemented according to its Acceptance Criteria and acceptance tests pass (per Microsoft Learn: Agile workflow in Azure Boards). Criteria that are vague or untestable break that gate.

Acceptance criteria must be independently testable with clear pass or fail outcomes; they should avoid vague terms and prefer measurable results — "the page loads within 2 seconds," not "the page loads quickly" (per AltexSoft: Acceptance Criteria). The guiding rule: if you cannot test it, it is not done.

## The Given/When/Then Structure
Given/When/Then comes from Gherkin, the language used by BDD tools such as Cucumber. It structures a single behavior with keywords (per Cucumber: Gherkin Reference):

- **Given** — the initial context or system state (something already true; the setup).
- **When** — the action or trigger being exercised.
- **Then** — the observable, expected outcome that determines pass or fail.
- **And / But** — extend any clause with additional context, actions, or outcomes.

A scenario represents one individual behavior. If a single scenario chains several When/Then pairs, that is a signal to split it into multiple scenarios (per Cucumber: Gherkin Reference). Setup shared across scenarios can be factored out (Cucumber calls this Background).

Given/When/Then is the scenario-oriented format. A simpler rule-oriented checklist format also exists and suits straightforward requirements, but checklists lack context and can fall short for complex behavior; the two formats can be mixed (per AltexSoft: Acceptance Criteria). What matters most is that each criterion is concrete and testable, whatever the format.

## The Testability Test
For any acceptance criterion, ask:

1. **Can I name a concrete passing case?** A specific input/state that makes it true.
2. **Can I name a concrete failing case?** A specific input/state that makes it false.
3. **Is the outcome observable and unambiguous?** Two people would agree on pass vs. fail without debate.
4. **Is it measurable where it needs to be?** Replace fuzzy words ("fast", "user-friendly", "properly") with concrete thresholds or observable behavior.

If any answer is "no," the criterion is not yet testable. Fuzzy adjectives are the most common failure — they hide an unmeasured expectation.

## Examples by Type
Each type shows a good version and a bad version with its rewrite.

### Feature
Acceptance criteria at the Feature level describe the observable result that signals the capability as a whole is delivered. The Acceptance Criteria field is available on Features (per Microsoft Learn: Query by titles, IDs, and rich-text fields).

- **GOOD (Feature: self-service password reset):**
  - Given a registered user on the sign-in page, When they request a password reset and follow the emailed link, Then they can set a new password and sign in with it.
  - Given an unregistered email address, When a reset is requested, Then no email is sent and the UI shows a neutral "if an account exists, a link was sent" message.
- **BAD:** "Password reset should work well and be secure."
  - *Why it fails:* "work well" and "be secure" have no passing or failing case; nothing is observable or measurable.
  - *Rewrite:* use the Given/When/Then pairs above, and add a measurable security criterion such as: Given a reset link, When more than 60 minutes have passed since it was issued, Then the link is rejected and the user is prompted to request a new one.

### User Story
For a story, criteria should yield acceptance tests and confirm the story can be closed (per Microsoft Learn: Agile workflow in Azure Boards).

- **GOOD (Story: shopper can save cart across sessions):**
  - Given a signed-in shopper with items in their cart, When they sign out and sign back in, Then the same items are still in the cart.
  - Given a shopper whose saved item is later discontinued, When they return, Then that item is removed from the cart and a notice is shown.
- **BAD:** "Cart should remember items."
  - *Why it fails:* no context, no triggering action, no observable outcome — and "remember" is undefined (for how long? across what?).
  - *Rewrite:* the Given/When/Then pairs above make the behavior and its edge case concretely testable.

### Task (no formal AC — "done" guidance instead)
Tasks carry only Title and Description and have no Acceptance Criteria field; a Task is the technical decomposition of a story (per Microsoft Learn: Best practices for Agile product management). Rather than formal AC, a Task needs an unambiguous completion condition stated in its Title or Description.

- **GOOD (Task: add unique index on Users.Email):** Description states the done condition plainly — "Migration adds a unique index on Users.Email; duplicate-email inserts are rejected at the database level; migration runs cleanly on a copy of production data." A reviewer can verify each clause.
- **BAD:** "Sort out the email thing."
  - *Why it fails:* no definable "done" — nobody can tell when the task is complete.
  - *Rewrite:* "Add a unique database index on Users.Email and update the migration; done when the migration applies successfully and inserting a duplicate email fails with a constraint error." This gives a concrete, checkable finish line without needing a formal AC field.

## Quick Reference
| | Acceptance Criteria field? | How to express "done" |
| --- | --- | --- |
| Feature | Yes | Given/When/Then scenarios for the capability's observable result |
| User Story | Yes | Given/When/Then (or testable checklist) yielding pass/fail acceptance tests |
| Task | No | Unambiguous completion condition in Title/Description; one verifiable result |
